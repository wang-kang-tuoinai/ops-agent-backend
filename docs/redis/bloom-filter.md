## 作用
布隆过滤器是一种O(K)复杂度判断你需要查询的信息是否在数据库里面(存在误判情况，你要查询的信息如果真的在数据库,那布隆过滤器一定会如实告诉你它在数据库（前提是你每一个入库的数据都在布隆过滤器里做了记录），但是如果你要查询的信息不在数据库，布隆过滤器也可能会判断他在数据库,这就是误判)，可以避免大量伪造不存在的Key查询数据库导致数据库压力暴增的问题。
## 原理
布隆过滤器可以大致分为两部分，一部分是一个大的bit数组，另一部分是几个Hash函数。当你成功往数据库存储了一个数据之后，你需要把这个数据的唯一身份标识(比如对于User的信息，可以选用User的ID，不管你怎么选，它一定要是全局唯一的)通过几个Hash函数进行计算，然后把得到的几个结果分别对bit数组大小取余，确保计算出来的数值落到bit数组里面，这就相当于bit数组的下标，然后把这些下标对应位置的0改为1，如果已经是1了，就不动。当一个请求带着key过来的时候(这个key要和你之前存数据的key是同一个属性，比如你存数据的时候使用User的ID去算下标，那么你取数据的时候也要使用ID)，我们那请求里面的Key同样通过上面存数据一样的几个Hash函数计算出下标，计算方法一模一样，然后我们观察其对应几个下表的值，如果全为1，说明可能存在与数据库，放行。如果有一个或多个不为1，说明它一定不存在，直接拦截并返回数据不存在的提示。这样只需要通过几个Hash计算，就能快速判断数据是否可能存在数据库中。
## 值得注意的点
### 1. 误判 
正如上面所说的，由于不同key的经过哈希计算出来得到的下表总会有重叠，所以如果某个key算出来的下标对应的值全部都被别的key变为1，会让布隆过滤器误以为数据库里存在但其实不存在。这就是误判产生的原因
### 2. bit数组的大小以及hash函数的个数
bit数组越大，当然误判率会低一点，但占用空间也会大一点。hash函数的个数其实要和bit数组的大小挂钩。这两个参数没有固定的值，应该根据实际业务来考虑。
### 3. 布隆过滤器是不能从里面删除1的
当你删除一个数据的时候，你可能想到把他也从布隆过滤器里移除，但是就像之前说到过的，你的bit为和其他数据的bit位是存在重叠的，你以为删除的是你自己的bit位，可能无意中就把其他数据的bit位给删了，导致其他数据存在于数据库中，但是布隆过滤器却说它不在数据库中。
### 4. 布隆过滤器的维护
 1. 对于单体项目可以在本地内存里维护一个布隆过滤器，但是这样有两个问题，第一个就是如果你的服务需要重启，那么你的内存里的布隆过滤器中的数据会消失。第二个无法解决的问题就是对于分布式微服务来讲，比如你的一个模块是负责用户注册的，那么你如果把布隆过滤器维护在这个服务内部，其他服务的布隆过滤器并不知道这个用户存在，同步比较麻烦。但好在现在Redis支持布隆过滤器，Redis里有完善的持久化机制，以及分布式集群，其他模块可以很轻松从Redis里面直到是否存在这个用户。
 2. 布隆过滤器需要定期重建，因为对于固定大小的bit数组，随着落库的数据越来越多，bit数组里的1的个数也会越来越多，误判率也随之升高，那么定期重建是降低误判率的一个好方法。
