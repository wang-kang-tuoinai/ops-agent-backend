## 为什么有时候单纯的sync.Mutex不行,而是需要分布式锁
因为如果只是单纯的sync.Mutex对于单实例还好，但是如果存在多个实例同时运行，那他就不能保证互斥了。
## 加锁
使用SET key value NX EX seconds命令
NX表示not exist 代表key不存在的时候才加锁，如果已经存在则失败。符合抢锁定义。
EX代表Expires 防止抢了锁的进程发生异常导致锁没有被正常释放的兜底措施
这是一个原子命令即加锁和设置超时是一个原子不可分割的，是安全的。
## 解锁
1. 解锁不能简单的用Del，而是要判断一下删除的是不是自己的锁。就比如A进程抢到了锁，进来，但是A进程由于数据库查询太慢了，或者是一些GC原因，导致业务还没有执行完，但是锁超时自动释放了，这时候B进程抢到了锁进来，执行业务逻辑，但这时候A业务逻辑执行完，它不看锁是不是自己加的，直接解了B进程的锁，这又会导致C进程抢锁进入临界区，这时候如果B执行完了，又释放了C的锁，就会导致无限套娃，临界区被彻底打破。所以一定要看一下是不是自己的锁，再决定去不去解锁。
2. 如果只是单纯的先去Redis查询再决定是否删除，那么查询和删除这两个独立的步骤之间也会有竞态条件。比如A进程先去查询锁是否是自己的，A发现锁确实是自己的，就在他准备删除的时候，结果由于GC的影响，解锁还没有执行，并且锁自动超时了，这时候B进程会进来，加锁，过了一会儿，A进程又继续执行解锁逻辑，又把B的锁给释放掉了。所以说我们要确保查询锁是否是自己的以及解锁变成一个原子不可分的操作，但是Redis里没有线程的命令，好在Redis支持Lua脚本，Redis执行Lua脚本的时候，不会接受其他客户端的请求，这就保证了lua脚本里的操作时原子的，所以可以把查询与解锁放在Lua脚本里面。

总的来说：加锁过程，通过Redis内置的原子命令把加锁设置超时时间变成原子性动作。解锁过程，通过Lua脚本，把查询锁是否是自己的与删除锁变成一个原子性动作。
